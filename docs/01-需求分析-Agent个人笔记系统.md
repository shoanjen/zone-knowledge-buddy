# 需求分析：基于 Agent 的个人笔记系统

> 版本 v0.3（已确认基线） · 日期 2026-10-19 · 状态：已确认
> 定位修正（2026-10-19）：按**计算机专业毕业设计**要求裁剪——Web 部署、单人使用、交互式报告；决策记录见 §11。
> 模型策略修订（2026-10-19，v0.3）：生成类任务**以云端 API 为主力**；本地模型仅作离线兜底，下载时只求速度，不装大模型（详见 §11 Q3）。
> 定位：本文档是需求分析，回答「做什么、为谁做、做到什么程度」；后续 PRD 与技术方案在此基础上展开。

## 1. 需求摘要

| 项目 | 内容 |
|------|------|
| 功能名称 | 基于 Agent 的个人笔记系统（暂名，可后续定名） |
| 功能背景 | 个人资料散落在 PDF / Word / Markdown / Excel / 网页中，格式异构、检索困难，知识整理全靠手工，成本高、难沉淀 |
| 目标用户 | 个人知识工作者：研究者、学生、职场人、内容创作者 |
| 核心场景 | 导入多格式资料 → Agent 解析与智能整理 → 生成报告 / 知识笔记 / 网页演示 → 沉淀为可检索、可对话的知识库 |
| 业务目标 | 单份资料从导入到产出可用笔记 ≤ 2 分钟；手工整理时间减少 70%+；生成内容 100% 可溯源到原文 |
| 优先级 | P0（毕设项目，MVP 先行） |
| 部署形态 | Web（B/S 架构，本机自托管），单用户 |
| 模型策略 | 云端 API（GLM / DeepSeek 等）为主力，本地小模型（Ollama，qwen3:4b 级）兜底可切换；资料默认本地存储 |
| 期望交付 | 毕设答辩前完成全功能闭环演示（约 3–4 个月开发窗口） |

## 2. 问题与机会

**现状痛点（Why）：**

1. **格式异构**：一份主题的资料往往横跨 PDF 论文、Word 报告、Excel 数据、网页收藏、零散 md 笔记，无法统一管理。
2. **整理成本高**：摘录、归纳、做笔记纯手工，读完不等于记住，更不等于能用。
3. **知识不可复用**：存量笔记是"死"的——检索靠关键词、无法跨文档关联、无法基于已有知识直接产出新东西（报告/汇报页）。
4. **输出断层**：从"资料"到"交付物"（给领导看的报告、给同学讲的演示页）之间缺少自动化桥梁。

**机会（What）：**

LLM Agent 具备"规划 → 调用工具（解析器/检索器/生成器）→ 反思修正"的能力，恰好可以承接这条链路：**把异构输入统一解析，把整理过程交给 Agent，把输出固化为可分享的知识资产**。

## 3. 目标用户画像

| 画像 | 典型代表 | 核心诉求 |
|------|---------|---------|
| 研究型 | 研究生、行业分析师 | 批量读论文/报告，快速产出文献综述、对比分析 |
| 职场型 | 产品经理、咨询顾问 | 会议纪要、竞品资料整理，快速产出汇报文档/演示页 |
| 学习型 | 学生、备考者 | 课件/教材转复习笔记，生成可讲解的网页 |

共同特征：**单人多设备使用、资料隐私敏感、愿意为"省时间"接受 AI 生成 + 人工校对的工作流**。

## 4. 用户故事与核心场景

### 4.1 用户故事

- 作为**研究者**，我希望导入 10 篇 PDF 论文，让 Agent 生成一份带引用的文献综述，以便快速掌握一个领域。
- 作为**职场人**，我希望粘贴一组网页链接，Agent 抓取正文并生成摘要笔记卡片，以便碎片信息不流失。
- 作为**学生**，我希望上传课件 PDF 和成绩 Excel，让 Agent 生成复习笔记和一页可讲解的网页，以便备考和分享。
- 作为**使用者**，我希望直接用自然语言提问（"这三份报告里关于成本的说法有什么冲突？"），Agent 基于我的知识库回答并给出原文出处，以便可信地取用知识。
- 作为**使用者**，我希望在 Agent 产出关键结论时人工确认，以便控制质量、避免幻觉扩散。

### 4.2 端到端核心流程

```
[输入] 上传文件 / 粘贴 URL / 拖拽批量导入
   ↓
[解析层] 按格式分发解析器 → 统一文档中间表示（结构化 Markdown + 元数据）
   ↓
[Agent 整理层] 意图理解 → 任务规划 → 调用工具(检索/摘要/提取/关联) → 生成 → 自检
   ↓                     ↑
   |                [人工确认节点]（可选，human-in-the-loop）
   ↓
[输出层] ① 报告(md/docx/pdf)  ② 知识笔记(卡片+双链+标签)  ③ 网页演示(HTML/幻灯)
   ↓
[沉淀层] 入库向量化 → 语义检索 / 知识图谱 / 对话问答
```

## 5. 功能需求分析（模块拆解）

### M1 多格式接入与解析（P0，地基）

| 功能点 | 说明 | 优先级 |
|--------|------|--------|
| PDF 解析 | 文本/标题层级/表格提取；扫描件走 OCR；公式与图片降级处理 | P0 |
| Markdown 解析 | 原生解析 + frontmatter 元数据 | P0 |
| 网页抓取 | URL 正文抽取（去导航/广告）；动态渲染页面用 headless 浏览器；失败降级为纯文本 | P0 |
| Word 解析 | docx 标题/段落/表格/图片 | P1 |
| Excel 解析 | 多 sheet、表头识别、数据类型推断，转为表格摘要+原始数据 | P1 |
| 统一中间表示 | 所有格式归一为「结构化文档模型」：章节树 + 块（段落/表格/图片）+ 元数据（来源/时间/作者） | P0 |
| 批量导入 | 拖拽上传、文件夹监控、URL 列表 | P1 |

**需求分析要点**：解析质量决定全局上限。扫描 PDF、跨页表格、公式是已知难点，MVP 允许"解析置信度低 → 标记提醒用户人工检查"的降级策略，而不是追求 100% 自动正确。

### M2 Agent 智能整理（P0，核心价值）

| 功能点 | 说明 | 优先级 |
|--------|------|--------|
| 意图理解 | 自然语言下达任务："把这几个 PDF 整理成对比报告" | P0 |
| 任务规划与执行 | Agent 拆解步骤、选择工具、执行、对结果自检与重试 | P0 |
| 摘要与提炼 | 全文摘要、章节要点、关键实体/数据提取 | P0 |
| 结构化提取 | 按用户模板抽取字段（如论文：方法/数据/结论） | P1 |
| 分类打标 | 自动归类到主题、生成标签 | P1 |
| 跨文档关联 | 相似度关联、冲突检测（两份资料说法不一致时提示）、知识图谱 | P2 |
| 人工确认节点 | 关键结论/入库前允许用户审核修改 | P1 |

**需求分析要点**：Agent 的价值不在"会写"而在"会整理"——多文档综合、去重、发现矛盾、按需重组。每条产出必须**附原文引用（可点击跳转）**，这是对幻觉的核心防线，应作为 P0 硬性需求。

### M3 输出生成（P0–P1，价值出口）

| 输出物 | 说明 | 优先级 |
|--------|------|--------|
| 知识笔记 | 卡片式结构化笔记（摘要/要点/引文/标签），支持编辑 | P0 |
| 报告 | 长文档生成，支持导出 md / docx / pdf，含目录与引用 | P1 |
| 交互式报告 | 单页 HTML：目录导航 + ECharts 交互图表 + 可折叠原文引用，可本地打开或部署分享 | P1 |
| 模板系统 | 用户自定义输出结构与风格（如"周报模板""读书笔记模板"） | P2 |

**需求分析要点**："网页演示载体"需进一步明确形态（见 §11 待确认问题 Q4）：是 reveal.js 类幻灯片，还是可交互的单页报告？建议 MVP 先做"单页图文 HTML"，成本低、复用 md 渲染管线。

### M4 知识库管理（P0 检索 / P1 图谱）

| 功能点 | 说明 | 优先级 |
|--------|------|--------|
| 笔记管理 | CRUD、文件夹/标签、版本历史 | P0 |
| 语义检索 | 向量化入库，按语义而非关键词检索 | P0 |
| 全文检索 | 关键词精确匹配 | P0 |
| 知识图谱视图 | 实体与笔记的关联可视化 | P2 |
| 外部互通 | 导入/导出 Obsidian/Notion 格式 | P2 |

### M5 对话交互（P0）

| 功能点 | 说明 | 优先级 |
|--------|------|--------|
| 知识库问答 | 与全部已入库内容对话，RAG + 引用溯源 | P0 |
| 任务面板 | 查看 Agent 任务进度、中间产物、失败重试 | P1 |
| 编辑器内对话 | 针对单篇笔记提问/改写 | P1 |

### M6 系统与配置（P0 最简）

| 功能点 | 说明 | 优先级 |
|--------|------|--------|
| 模型配置 | 模型供应商管理：云端 OpenAI 兼容 API（默认生效）与本地运行时（Ollama / LM Studio，小模型兜底），可切换、可检测连接，界面标识当前生效配置 | P0 |
| 数据管理 | 本地存储、备份导出 | P0 |
| 成本可见 | Token 用量/费用统计 | P1 |
| 多用户/同步 | 账号体系、多端同步 | P2（个人版暂不做） |

## 6. 非功能需求

| 维度 | 需求 |
|------|------|
| 性能 | 100 页以内 PDF 解析 ≤ 30s；单文档「导入→笔记」≤ 3 分钟（LLM 推理为主要耗时，属预期）；检索响应 ≤ 1s |
| 规模 | 单知识库 ≥ 1000 份文档可用 |
| 准确性 | 笔记/报告中的事实性陈述 100% 带原文引用；解析失败必须显式提示，禁止静默丢弃 |
| 隐私安全 | 资料存储与向量库始终本地；生成类推理默认云端，界面明确标识当前推理位置与 Token 用量；可随时切换本地小模型实现全离线；文档来源与解析状态透明可查 |
| 成本 | 云端按 Token 计费，任务级用量与耗时全程记录（兼作论文性能分析数据），提供用量统计与预算提醒；本地小模型零费用，用于离线兜底与低成本联调 |
| 硬件与推理 | 本地运行时（Ollama 默认 / LM Studio 可选）仅运行小参数量模型（qwen3:4b 级）+ 向量模型 bge-m3，Apple Silicon 8GB+ 内存即可；生成质量主力靠云端 API，不依赖本地大模型；本地上下文有限，长文采用 Map-Reduce 分块摘要 |
| 可扩展 | 解析器、输出生成器以插件化方式注册，新增格式不动核心 |

## 7. 竞品参考与差异化

| 竞品 | 相似点 | 差异化机会 |
|------|--------|-----------|
| NotebookLM | 多源上传 + 对话 + 报告 | 它的资料与推理都是云端黑盒、来源类型受限；本项目自托管、资料始终本地、Agent 可编排、输出可定制（推理可切本地小模型全离线） |
| Notion AI | 笔记 + AI 写作 | 整理的是"笔记内部"，不做多格式异构资料的解析入库 |
| Obsidian + 插件 | 双链、本地优先 | 整理仍靠手工 + 插件拼装，无开箱 Agent |
| Recall / readwise 类 | 网页收藏摘要 | 输出形态弱，无报告/演示页生成 |

**差异化定位**：**"异构资料 → Agent 整理 → 可交付输出"的全链路个人工具**，而不是又一个笔记编辑器或又一个 AI 问答框。

## 8. 技术选型（已确定）

| 层 | 选型 | 理由 |
|----|------|------|
| 模型推理 | 统一 LLM 网关（OpenAI 兼容协议）：云端 API（GLM / DeepSeek 等）为生成主力（默认生效）；本地 Ollama（qwen3:4b 小模型 + bge-m3）兜底，LM Studio 为可选本地运行时（MLX 提速）；向量模型固定本地以保持向量库一致 | 三类端点同一套协议，切换即改配置；本地只装小模型，优先速度 |
| 解析 | PyMuPDF、python-docx、openpyxl+pandas、trafilatura+Playwright、markdown-it | Python 生态最全，均为成熟库，工作量可控 |
| Agent 编排 | 自研 ReAct 风格 planner–executor 循环 + 工具注册表 | 毕设需可解释、可画流程图、可写算法细节，自研比套框架更有论文内容 |
| RAG | 分块 → bge-m3 向量化 → Chroma 向量库 → chunk_id 引用溯源 | 轻量嵌入式，无外部服务依赖 |
| 后端 | Python FastAPI + SQLAlchemy + SQLite | 单机部署零运维 |
| 前端 | Vue 3 + Vite + Element Plus + ECharts | 主流、组件全，图表能力契合交互式报告 |
| 报告输出 | Jinja2 渲染自包含单页 HTML（内联 ECharts、目录导航、引用折叠） | 交互式报告的核心交付形态 |

> 详细设计（架构图、数据模型、Agent 流程、评测方案、里程碑）见《02-总体设计与实施计划-毕设版》。
> 选型已按毕设可行性收敛：去掉 Postgres/pgvector/对象存储等偏生产组件。

## 9. 风险评估

| 风险 | 描述 | 影响 | 应对 |
|------|------|------|------|
| 解析质量 | 扫描 PDF、跨页表格、公式解析失败或失真 | 高 | 置信度标记 + 人工校对入口；难点格式后期引入版面分析模型 |
| LLM 幻觉 | 生成的笔记/报告夹带原文不存在的内容 | 高 | 强制引用溯源、生成后自检（对照原文校验）、人工确认节点 |
| 成本失控 | 长文档、批量任务 Token 消耗大 | 中 | 分层模型、缓存、用量统计与预算提醒 |
| 网页抓取受阻 | 反爬、登录墙、动态渲染失败 | 中 | headless 浏览器 + 多策略降级；明确提示失败原因 |
| 需求蔓延 | 想做的输出形态和集成太多 | 中 | 严格按 MVP 边界迭代（见 §10） |

## 10. MVP 边界与迭代路线（建议）

**MVP（≈毕设中期检查）**：五种格式基础解析（PDF/Word/MD/Excel/网页）→ Agent 摘要整理生成知识笔记（带引用）→ 入库向量化 → 语义检索 + 知识库问答（带引用）。

**V1（≈答辩版本）**：交互式报告生成（ECharts 图表、目录导航、引用折叠）、任务面板 + 人工确认节点、报告 HTML 导出、极简登录。

**V2（答辩后可选，不计入毕设工作量）**：知识图谱、跨文档冲突检测、模板系统、Obsidian/Notion 互通、多端同步。

## 11. 决策记录（2026-10-19 已确认）

| # | 问题 | 决策 |
|---|------|------|
| Q1 | 部署形态 | Web 形式部署：B/S 架构，本机自托管（FastAPI + Vue 3） |
| Q2 | 用户范围 | 个人使用、单用户；保留一个极简登录以保证系统完整性 |
| Q3 | 模型策略 | **云端为主、本地小模型兜底**（2026-10-19 修订，原为「本地为主」）：生成类任务默认走云端 OpenAI 兼容 API（GLM / DeepSeek 等）；本地运行时（Ollama 默认 / LM Studio 可选）仅作离线兜底与低成本联调，模型选小参数量（qwen3:4b，约 2.5GB），下载只求速度、不装 8B 级大模型；向量模型固定本地 bge-m3，保证向量库语义一致 |
| Q4 | 网页演示载体 | 交互式报告：单页 HTML，含目录导航、ECharts 交互图表、可折叠原文引用 |
| Q5 | Obsidian/Notion 互通 | 不做，移入答辩后可选扩展 |

**范围基线**：按计算机毕业设计要求合理裁剪——单人、单机；推理默认云端、可一键切换本地小模型；重心放在「多格式解析 → Agent 整理 → 引用溯源问答 → 交互式报告生成」的完整闭环与可评测性上，不追求生产级多用户/同步/高可用。
